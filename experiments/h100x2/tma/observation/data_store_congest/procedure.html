2 · Inside one copy CTA

Threads and shared memory of one copy CTA

Every CTA has 1024 threads and 196,864 bytes of shared memory. Copy threads and co-runner threads use separate named barriers, so in the same-SM tests neither group waits for the other.

3 · Timing model, per chunk

How two staging slots keep the TMA unit busy

Chunk j goes into slot j mod 2. Before filling it, thread 0 waits until the TMA unit has finished reading the chunk that used that slot before (cp.async.bulk.wait_group.read 1). That wait is the slot wait. The fill and its two barriers make up the fill share.

  • Below the plateau (1–8 copy CTAs), one CTA sends about 51 GB/s; slot wait is about 39% of thread 0's loop.
  • On the plateau (12+ CTAs), NVLink is full, the TMA unit reads slots out more slowly, and slot wait grows: 63% at 12 CTAs, 72% at 16, 89% at 48.
  • One slot leaves no overlap between fill and read-out: 35.8 GB/s per CTA. A third slot adds nothing.
  • Code: issueBulkCopy in tma_congest.cu (ring index, waitForBulkSourceReads, fill, startBulkStore).
4 · Timing model, per transfer

What each timer of one transfer covers

Every timer runs on one GPU's clock. Source and destination timers are never compared with each other; the two GPUs coordinate only through signals.

  • Bulk completion wait (A17) runs from the last bulk store started until cp.async.bulk.wait_group 0 returns: the writes of this CTA have completed. It grew from about 2.4 to 4.1 µs with a TMA writer on the same SMs.
  • Ordering (A4) is fence.proxy.async.global plus a system fence; only thread 0 fences, because only it wrote to the peer.
  • A thread-store writer on the same SMs shows up in the fill share instead (19% → 37%), and slot wait falls.

6 · Resource management: SMs

Which SM does what

Both GPUs launch one CTA on every SM (cooperative launch). Each CTA reads its SM ID and takes the role the host's role table gives that SM. The tables come from plan 07's measured SM-to-GPC map; the maps below are copied from three real run records.

Copy CTA Co-runner CTA Copy CTA hosting a co-runner Receiver CTA Idle CTA (holds the SM)
  • One CTA per SM is enforced three ways: 196,864 bytes of shared memory per CTA (more than half an SM), an occupancy check that must return 1, and a check that no two CTAs report the same SM ID.
  • SM budget: 16 copy + 64 co-runner CTAs ≤ the 124 SMs the map places in GPCs. SMs 124–131 were never placed by cluster launches and stay idle.
  • G6 has 18 SMs: the copy takes 16; the other 2 stay idle.
