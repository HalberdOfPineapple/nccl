# Observation series: observing thread-level remote stores in scale-up communication

## Goal

Decide what the observation plane of a scale-up communication diagnosis system should capture. Start from one healthy, minimal data path, a GPU thread issuing stores into a peer GPU's memory over NVLink (a push), inject one well-defined problem at a time, and ask which observations separate each injected problem from the healthy run and from the other problems.

Framing: [large_scale_ml_diagnosis_framework.html](../../../../notes/large_scale_ml_diagnosis_framework.html) (observation plane, detection, root-cause analysis) and [scale_up_communication_problem_matrix.md](../../../../notes/scale_up_communication_problem_matrix.md). This series covers the first row of the matrix, thread-issued peer loads/stores, in its push form, across all five problem columns.

## Why push changes what can be observed

- Peer stores are posted operations: issue is distinct from remote completion. The issuing warp can stall on source-load dependencies, instruction issue, or memory-system backpressure as well as ordering operations. Timers around an issuing loop do not measure individual remote-store latency.
- Completion requires a documented cross-device ordering and notification protocol; a fence alone is not a receiver acknowledgement. Measure issue, ordering/notification, receiver observation, and acknowledgement separately where implemented. Buffer-reuse waiting and receiver data waiting are different dependencies.
- The memory that gets busy is the destination GPU's, which moves the contention questions to the other endpoint.

## Rules for exploratory observation plans

Apply these rules alongside [experiment conventions](../../../CLAUDE.md). The purpose is to discover useful evidence, not to prescribe an already validated signature or online decision threshold. For this series, include **Observations and interpretation** after each experiment's procedure, supplementing the standard plan structure with the detail below.

1. **Start with a question and competing explanations.** Identify the matrix cell, the modeled interference, and what throughput alone cannot distinguish. State communication throughput/duration as the primary performance outcome and present its valid reference comparison before secondary co-runner performance; a copy-disabled arm is not a healthy-copy baseline. Separate the outcome (communication slowed), pressure validation (the co-runner actually ran), and localization/mechanism evidence (which part of progress changed).
2. **Define the measured operation before instrumenting it.** Specify endpoints, useful bytes, issue and completion boundaries, and any receiver/control work. A kernel duration may include co-runner startup/shutdown; a posted-store loop is not completed-transfer latency. Use per-device durations unless cross-device clocks have been calibrated.
3. **Establish a matched reference and a severity ladder.** Present all fixed and varied knobs in configuration tables and emphasize the independent variable and its values in bold; state which other knobs are held fixed within each comparison. Configuration labels in setup/result tables and figures must include all coupled launch dimensions, with workload roles explicit (for example, communication: 4 CTAs × 256 threads/CTA). Use separate columns or complete tuples; never label a configuration by only the swept value. Keep the sweep identity separate when the same full configuration is repeated in different sweeps. Characterize healthy concurrency and traversal first. Each perturbation then uses a no-co-runner control with identical launch/resource reservations, buffers, and protocol. Calibrate at least mild, moderate, and strong achieved pressure rather than assuming CTA count or pacing is proportional to interference. A no-slowdown case is useful evidence, not a failed experiment.
4. **Specify acquisition, not just metric names.** Use a table with observation, instrument/endpoint/window, expected signature or competing explanation, and limitation. Name timer boundaries, byte/progress counters, relevant profiler sections or instruction PCs, and device telemetry. Separate cheap instrumentation from timeline checks and intrusive hardware-counter passes. Exact counter names must be resolved for the installed GPU/tool version rather than invented.
5. **Retain a common core across all cases.** Collect useful bytes, completed duration, per-CTA issue/protocol durations and SM/role mapping, achieved co-runner activity/overlap, and both endpoints' operating state wherever available. This supports cross-experiment comparison. The current harness subset and metric registry are in [00_common_setup.md](00_common_setup.md); remaining profiler observations are candidates until validated. Reconcile older plans with that registry before implementation, and record missing measurements explicitly.
6. **Make attribution scope explicit.** A device-wide memory counter includes all activity; a fused-kernel counter includes all CTA roles. Prefer source/PC attribution for communication instructions when supported; otherwise report aggregate pressure. Source-load stalls, store-path backpressure, completion signaling, and power/clock effects can overlap. A busy endpoint or a long fence does not uniquely identify a physical queue, HBM bottleneck, or fabric component.
7. **Design profiling around the actual interference.** First run unprofiled paired measurements, then sparse device probes, timelines, and selected counter passes. Confirm overlap and launch placement after adding probes. Record replay, cache/clock controls, counter permissions, tool versions, and probe overhead. Confirm that a requested range actually contains measurements; a zero exit status or an exported file can still mean no range was collected. Reject profiler passes that serialize or otherwise remove the tested interaction; independent source-only and destination-only profiles are complementary runs, not a simultaneous trace.
8. **Use controls to test interpretation.** Compare communication alone, co-runner alone, and concurrent work; move the same pressure workload between endpoints with matched role reservations. Hold access pattern and useful bytes fixed. Optional active tests belong in separate diagnostic runs and must not silently replace the primary workload. Match the active duration and binary revision of workload-alone controls to concurrent runs where possible. Observe both workloads: unchanged communication throughput does not show that the other workload is unaffected. Co-runner-alone subtraction is not exact traffic attribution under concurrency.
9. **Plan repeatability and negative results.** Use at least five interleaved healthy/perturbed pairs per calibrated level, retain run order and environmental state, and repeat the no-pressure reference after a sweep. Report paired differences and distributions, plus the effect size prescribed in `experiments/CLAUDE.md`; if healthy IQR is zero, report that and use raw differences rather than dividing by zero. Separate absence of degradation from missing counters, inadequate sampling, or absent overlap.
10. **Evaluate distinguishability without leaking injection labels.** For each candidate signal, ask whether it separates healthy/perturbed runs, then whether it separates similar slowdowns from different injections. Labels and knob values establish evaluation context; they cannot themselves count as discovered diagnostic signals. Report unresolved pairs and the additional observation needed. Record acquisition rights, overhead, and whether a signal could be routine or only targeted before proposing it for the observation plane.

Throughput, duration, and achieved-rate figures use zero-based y-axes with rounded upper bounds and consistent scales across comparable panels. Small differences belong in precise result tables, not in narrowly autoscaled axes.

The series deliverable is evidence about candidate observations: measurement definition, coverage, healthy/perturbed separation, cross-problem ambiguity, and collection cost. Detection rules and verified causal mechanisms require additional validation; mitigation remains optional in the broader framework.

For memory-pressure experiments, calibrate achieved read bandwidth across CTA count and threads per CTA before selecting the pressure sweep. Include intermediate configurations such as 64 read CTAs where feasible, and extend request supply if the strongest feasible point is still improving. Repeat the calibrated settings with communication, reporting both standalone and concurrent achieved rates. Account explicitly for shared source-SM budgets and coupled harness knobs; a nominally maximal CTA count is not evidence of maximal memory bandwidth.
