NCCL Device API: a code walkthrough

This page explains how a user CUDA kernel communicates with other GPUs directly from device code. It follows four example kernels from docs/examples/06_device_api and traces every call through NCCL's headers and the host runtime, down to the NVLink stores, NIC work requests and proxy descriptors that actually move the data.

Linked badges open the file at the v2.32.3-1 tag on GitHub; badges such as core__funcs.h:146 give the file and line in this checkout. Chain tags: host runs on the CPU in the calling thread, device is inlined into the user kernel, nic is NIC hardware, and proxy is a CPU helper thread.

1What the device API is

The classic NCCL host API (ncclAllReduce, ncclSend, …) enqueues work that NCCL's own kernels run, and the CPU decides what happens and when. The device API turns this around. NCCL hands the application a small, by-value ncclDevComm struct plus ncclWindow_t handles to registered memory, and the application's own kernel calls header-only, inlined device functions to read and write peer memory, synchronise with peers, and post network operations. Communication can therefore be fused into compute kernels with no host round-trip.

LSA: Load/Store Accessible

Peers in the same NVLink domain (the LSA team) have their memory mapped into your VA space. You get a raw pointer and use ordinary loads and stores.

GIN: GPU-Initiated Networking

For peers that are not load/store reachable, a GPU thread posts one-sided RDMA puts with remote signals, either straight to the NIC (GDAKI/EFA-GDA/GPI) or through a CPU proxy.

CFT: CUDA Fabric Transport

For large multi-node NVLink domains (sm_100+, CUDA 13.3+), puts, reductions and gets go through fabric logical endpoints, with counted completion.

3Core concepts

3.1 ncclDevComm: the by-value device communicator

ncclDevComm is a plain struct (impl/comm__types.h:28) that you pass to the kernel by value. It holds no pointers to host memory. Everything it references (windows, resource buffers, GIN handles) is already device-accessible.

struct ncclDevComm {
  unsigned int magic, version;            // ABI versioning (see src/devcomm/devcomm_v*.cc compat shims)
  int rank, nRanks;   uint32_t nRanks_rcp32; // world team; *_rcp32 = reciprocal for fast int div
  int lsaRank, lsaSize; uint32_t lsaSize_rcp32; // my position in the load/store team
  ncclDevCommWindowTable_t windowTable;  // device-side VA→window lookup (ncclFindWindow)
  ncclWindow_t resourceWindow;           // symmetric buffer holding barrier state etc.
  ncclResourceWindow_vidmem_t resourceWindow_inlined; // {lsaFlatBase, stride4G, mcOffset4K} copied inline
  ncclGinBarrierHandle_t hybridDenseGinBarrier;
  ncclMultimemHandle_t lsaMultimem;      // NVLS multicast base for the LSA team
  ncclLsaBarrierHandle_t lsaBarrier;     // ← reqs.lsaBarrierCount
  ncclGinBarrierHandle_t railGinBarrier; // ← reqs.railGinBarrierCount
  uint8_t ginConnectionCount, backendIndex;
  uint8_t ginNetDeviceTypes[NCCL_GIN_MAX_CONNECTIONS]; // PROXY / GDAKI / GPI / EFA_GDA per connection
  void* ginHandles[NCCL_GIN_MAX_CONNECTIONS];          // backend GPU context arrays
  int ginSignalCount, ginCounterCount;
  uint64_t* ginSignalShadows;            // per-context expected-value shadows
  uint32_t ginContextCount; int ginConnectionStride, ginContextStride;
  uint32_t* abortFlag;
  ncclLsaBarrierHandle_t hybridLsaBarrier;   // ← reqs.barrierCount (ncclBarrierSession)
  ncclGinBarrierHandle_t hybridRailGinBarrier;
  ncclGinBarrierHandle_t worldGinBarrier;    // ← reqs.worldGinBarrierCount
  // ... CFT: cftRank/cftSize, ucLeId/mcLeId, cftBarrier, cftMultimemBarrier
};

3.2 Windows and the flat LSA virtual address space

An ncclWindow_t is a device pointer to an ncclWindow_vidmem (impl/core__types.h:30). Its key fields are lsaFlatBase (where LSA rank 0's copy of this window lives in my VA), stride4G (the distance between ranks' copies, in units of 4 GiB), lsaRank/worldRank, mcOffset4K (multicast offset), ginOffset4K and ginWinsDefaultBackend[] (NIC registration handles).

The trick that makes LSA pointer lookup cost a single integer add: on first use, the host reserves one huge VA range of lsaSize × bigSize bytes (dev_runtime.cc:397). Here bigSize is at least the largest GPU memory in the team, rounded up to 4 GiB (dev_runtime.cc:200). Every peer's physical allocation is mapped at the same bigOffset inside that peer's slot.

3.3 Teams

A ncclTeam is just {nRanks, rank, stride} (core.h:51): an arithmetic progression of world ranks containing the caller. Device-side constructors are trivial reads of ncclDevComm (core__funcs.h:16-73), and conversion is world = comm.rank + (peer − team.rank)·team.stride (core__funcs.h:93).

Tag types ncclTeamTagWorld, ncclTeamTagLsa and ncclTeamTagRail are empty structs. They select convenience constructors that bind the team and the matching barrier handle stored in ncclDevComm.

3.4 Coop: who participates in a call

Almost every device API call takes a Coop object as its first argument. It is NCCL's minimal version of CUDA cooperative groups, providing thread_rank(), size() and sync() (coop.h). All threads in the coop must make the call together. NCCL then typically elects thread_rank()==0 to do serial work (posting a NIC WQE) or spreads per-peer work across the threads (barrier arrivals), and brackets the work with coop.sync().

4Host-side setup: the shared prologue of every example

All four examples follow the same host recipe. The figure below shows it as a timeline, and the subsections trace the two NCCL-specific calls.

Both calls are "group-aware".Each call opens an internal group (ncclGroupStartInternal), enqueues a task on comm->devrState, and closes the group. If the application wraps several registrations in ncclGroupStart/End, they are batched and executed together when the group ends, by group.cc:372 ncclCommGroupRegisterSymmetric. With NCCL_ENQUEUE_REARCH_ENABLE, the same work goes through ncclMgmtTaskEnqueue instead.

5Example 1 · AllReduce over LSA (pure load/store)

Source: 06_device_api/01_allreduce_lsa/c/main.cu. This section follows the kernel one line at a time. For each line it shows the code that actually runs once NCCL's inline functions are expanded, and traces it with real numbers.

5.1 The concrete case we will trace

  • One machine with 4 H100 GPUs connected by NVLink. There is one process (rank) per GPU: ranks 0, 1, 2 and 3.
  • Each rank has a sendbuf and a recvbuf of 1,048,576 floats (4 MiB). Before the kernel, rank r fills its sendbuf with the value r.
  • Goal: afterwards, every element of every rank's recvbuf is 0 + 1 + 2 + 3 = 6.
  • Each rank launches the same kernel with 16 blocks × 512 threads. The four launches run at the same time, one per GPU.
  • When we follow "one thread", it is rank 2, block 5, thread 7.

Terms used below, in plain words:

TermMeaning in this example
LSA ("load/store accessible")The GPUs whose memory this GPU can read and write with ordinary pointers over NVLink. Here that is all 4 GPUs, so "LSA rank" and "rank" are the same number (the example checks props.nLsaTeams == 1 to make sure).
devComm (ncclDevComm)A plain struct of numbers and GPU pointers that the host filled in with ncclDevCommCreate and passed to the kernel as an argument. The fields this example reads: rank, nRanks, lsaRank, lsaSize, lsaBarrier and the location of the "resource buffer" (5.2).

5.2 What is in memory when the kernel starts

Three things prepared by the host code decide everything the kernel does.

(a) One big address range that shows all 4 GPUs' memory

On each GPU, NCCL reserves a range of virtual addresses (addresses only, no memory behind them yet) that is 4 × 80 GiB long. The 80 GiB is bigSize: the largest GPU memory among the ranks (the H100s here report 81,559 MiB ≈ 79.6 GiB), rounded up to a multiple of 4 GiB (dev_runtime.cc:193-200). The range is split into 4 slots, one per GPU. When you register a buffer, NCCL maps every GPU's copy of it into that GPU's slot, at the same offset inside each slot. NVLink lets a GPU access pages that belong to another GPU, so after this mapping an ordinary pointer into slot 3 reads GPU 3's memory.

(b) The window structs sendwin and recvwin

sendwin points to this struct in GPU memory (only the fields this kernel uses are shown; definition at impl/core__types.h:30). The values are rank 2's, with the example addresses from the figure:

sendwin->lsaFlatBase = 0x7F00_0060_0000   // where GPU 0's sendbuf appears in MY address range
sendwin->stride4G    = 20                  // distance between slots, in units of 4 GiB (20 × 4 GiB = 80 GiB)
sendwin->lsaRank     = 2                   // my own slot number

(c) The barrier flags

On the host, the example sets reqs.lsaBarrierCount = 16 before calling ncclDevCommCreate. That asks NCCL for 16 independent barriers among the LSA GPUs, one per block. NCCL then allocates, on every GPU, an array of (3·16 + 16·4) = 112 uint32_t = 448 bytes and fills it with zeros (formula at nccl_device/lsa_barrier.cc:14). The array lives inside a larger allocation called the resource buffer, which NCCL maps into the same 4-slot address range as your buffers. So GPU 2 can write into GPU 0's flag array with a normal store.

Array indexWhat it holdsUsed in this example?
0 … 15saved epoch of barrier 0…15, multicast variantno
16 … 31saved epoch of barrier b at [16 + b]: how many times block b has passed its barrier in earlier kernelsyes
32 … 47multicast inboxno
48 … 111inbox: [48 + b·4 + s] is written only by GPU s, to say "my block b has reached round n"yes

devComm.lsaBarrier is the receipt for that allocation, two numbers {bufHandle, nBarriers} (impl/lsa_barrier__types.h:13). nBarriers is 16. bufHandle is where the array starts inside the resource buffer, in units of 128 bytes. To find the array on GPU p, the kernel uses the same slot arithmetic as for windows: resourceBufferOfGPU0 + p × 80 GiB + bufHandle × 128. The resource buffer's address and slot stride are copied into devComm.resourceWindow_inlined, so this needs no extra lookup.

5.3 The kernel, line by line

Each step shows the original line, then the code that effectively runs. This is NCCL's inline functions expanded by hand, with names simplified and the multicast branches removed because this example doesn't use them. Function names and source lines are listed after each step for readers who want to check.

The shorthand used in the expanded code:

// bar(p) = address of the 112-entry flag array on GPU p, as seen by this GPU
uint32_t* bar(int p) {
  char* gpu0 = devComm.resourceWindow_inlined.lsaFlatBase;      // GPU 0's resource buffer in my range
  return (uint32_t*)(gpu0 + p * (devComm.resourceWindow_inlined.stride4G * 4GiB)
                       + devComm.lsaBarrier.bufHandle * 128);
}

Step 1 · line 68: create the barrier object

ncclLsaBarrierSession<ncclCoopCta> bar { ncclCoopCta(), devComm, ncclTeamTagLsa(), blockIdx.x };

What the arguments mean:

  • ncclCoopCta(): "the whole block (all 512 threads) calls this together". Inside NCCL this choice only decides two things: sync() becomes __syncthreads(), and threads are numbered by threadIdx.x.
  • ncclTeamTagLsa(): an empty marker type. Passing it picks the constructor that means "synchronise with all GPUs in my LSA group, using the flag array created for lsaBarrierCount". That constructor just calls the general one with those two things filled in (lsa_barrier__funcs.h:33):
    • The group is ncclTeamLsa(devComm), which returns the three numbers {nRanks = devComm.lsaSize = 4, rank = devComm.lsaRank = 2, stride = 1} (core__funcs.h:26).
    • The flag array is devComm.lsaBarrier, the {bufHandle, nBarriers = 16} receipt from 5.2(c).
  • blockIdx.x: which of the 16 barriers this block uses. Block 5 on every GPU uses barrier 5, so block 5 only ever waits for the four "block 5"s.

What runs:

const int R  = devComm.lsaSize;        // 4 GPUs in the group
const int me = devComm.lsaRank;        // 2
const int b  = blockIdx.x;             // 5
uint32_t epoch = bar(me)[16 + b];      // how many times barrier 5 was passed before. 0 on the first launch

Nothing is communicated yet. The object just remembers R, me, b and epoch, the last in a register.

Step 2 · line 69: first barrier, "is everyone here?"

bar.sync(ncclCoopCta(), cuda::memory_order_acquire);

sync = arrive (tell the others "I'm here") followed by wait (wait until all others said so). What runs:

__syncthreads();                                   // all 512 threads of the block got here

// ---- arrive: threads 0, 1, 2 each notify one other GPU ----
if (threadIdx.x < R - 1) {
  int peer = threadIdx.x + (me <= threadIdx.x ? 1 : 0);   // skip myself: threads 0,1,2 → GPUs 0,1,3
  store_relaxed(&bar(peer)[48 + b*R + me], epoch + 1);   // write "1" into peer's inbox slot for (block 5, sender 2)
}

// ---- wait: threads 0, 1, 2 each wait for one other GPU ----
if (threadIdx.x < R - 1) {
  int peer = threadIdx.x + (me <= threadIdx.x ? 1 : 0);
  while (load_acquire(&bar(me)[48 + b*R + peer]) < epoch + 1) {
    // spin. Every 10,000 polls, also check devComm.abortFlag (null for user comms)
  }
}
epoch = epoch + 1;                                 // now 1
__syncthreads();                                   // the other 509 threads wait here for threads 0-2

Why this first barrier is needed. Step 4 reads the other GPUs' sendbuf. Each rank fills its sendbuf with cudaMemcpy before launching the kernel. When GPU 0's block 5 has stored its flag, GPU 0's kernel is running, so the copy GPU 0 issued before the launch has finished. The barrier also stops a fast GPU from writing into a slow GPU's recvbuf while that GPU might still be using it for something earlier.

The memory_order_acquire argument only changes the wait: the flag loads are acquire loads, so data read after the loop is not read early. The store side gets releaseOrderOf(acquire) = relaxed, so no fence is emitted before the flag stores (utility.h:328).

Code: lsa_barrier__funcs.h:165 sync → :55 arrive → lsa_barrier__types.h:42 ucInbox → core__funcs.h:274 ncclGetResourceBufferPeerPointer; wait → lsa_barrier__funcs.h:85 waitInternal. The real wait compares got - (epoch+1) <= 0x7FFFFFFF rather than <, so it stays correct when the 32-bit counter wraps around.

Step 3 · lines 76–77: decide which elements this thread handles

const int globalTid      = threadIdx.x + blockDim.x * (rank + blockIdx.x * nRanks);
const int globalNthreads = blockDim.x * gridDim.x * nRanks;

Plain arithmetic, no NCCL calls. All threads on all 4 GPUs together form one big pool of 512 × 16 × 4 = 32,768 threads, and each array element is handled by exactly one of them. For our thread: globalTid = 7 + 512 × (2 + 5 × 4) = 11,271, and it handles elements 11,271, 44,039, 76,807, … (adding 32,768 each time). That is 32 elements in total.

Put differently: the array is cut into 2,048 chunks of 512 elements, and chunk k goes to rank k % 4, block (k / 4) % 16:

chunk01234…22…6364…
handled by (rank, block)0,01,02,03,00,1…2,5…3,150,0…

Step 4 · lines 83–87: read the 4 inputs and add them

for (int peer=0; peer<nRanks; peer++) {
  float* sendPtr = (float*)ncclGetLsaPointer(sendwin, sendoffset, peer);
  v += sendPtr[offset];
}

What ncclGetLsaPointer runs (core__funcs.h:146):

char* base = sendwin->lsaFlatBase;                      // 0x7F00_0060_0000 (GPU 0's sendbuf)
uint32_t s = sendwin->stride4G;                         // 20
return base + (uint64_t)(peer * s) * 4GiB + sendoffset;   // sendoffset is 0 here

(The source writes the multiplication by 4 GiB as add4G(base, peer*s), which adds peer*s to the upper 32 bits of the address; utility.h:171.) For our thread at offset = 11,271:

peersendPtraddress of sendPtr[11271]physically onvalue read

(11,271 × 4 bytes = 0xB01C.) After the loop, v = 6. These are ordinary ld.global instructions. NCCL is not involved in the transfer: the GPU's memory system sends the request over NVLink because of how the page is mapped.

Note that ncclGetLsaPointer takes an LSA index (0…lsaSize−1), not a world rank. The kernel can pass peer from 0…nRanks−1 only because this example has a single LSA group, so the two numberings coincide.

Step 5 · lines 89–92: write the sum to all 4 receive buffers

for (int peer=0; peer<nRanks; peer++) {
  float* recvPtr = (float*)ncclGetLsaPointer(recvwin, recvoffset, peer);
  recvPtr[offset] = v;
}

The same address arithmetic, using recvwin. Our thread stores 6 into element 11,271 of the recvbuf on GPUs 0, 1, 2 and 3: three remote NVLink stores and one local store. No other thread anywhere writes element 11,271, so there is no conflict. After all 32,768 threads finish steps 4–5, each element of each recvbuf has been written exactly once.

Step 6 · line 97: second barrier, "everyone has finished writing"

bar.sync(ncclCoopCta(), cuda::memory_order_release);

The same code as step 2, with two differences:

__syncthreads();
cuda::atomic_thread_fence(cuda::memory_order_release, cuda::thread_scope_system);   // NEW: added because of "release"
if (threadIdx.x < R - 1) { /* store epoch+1 = 2 into bar(peer)[48 + b*R + me] */ }
if (threadIdx.x < R - 1) { /* spin until bar(me)[48 + b*R + peer] >= 2, using relaxed loads */ }
epoch = epoch + 1;                                 // now 2
__syncthreads();

The fence makes the GPU finish pushing out this block's earlier stores (the 4 stores per element from step 5) before the flag stores that follow. So when GPU 0 sees "2" in its slot from GPU 2, all of GPU 2 block 5's writes into GPU 0's recvbuf have already landed. Once a block passes this barrier, the matching block on every GPU has finished its part, and every element of this GPU's recvbuf is final. The spin loads are relaxed (acquireOrderOf(release) = relaxed, utility.h:323), because nothing in this kernel reads recvbuf afterwards. The host reads it after the kernel ends, and kernel completion already makes all writes visible.

Step 7 · line 98: closing brace, the destructor saves the epoch

if (threadIdx.x == 0) bar(me)[16 + b] = epoch;   // store 2
__syncthreads();

Flags are never reset to zero. Next time this kernel runs, step 1 reads 2 and the two barriers use flag values 3 and 4. Because values only increase, a flag left over from an earlier launch can never satisfy a wait in a later one. This is also why the barrier object cannot be copied (lsa_barrier.h:28): two copies would each write their own epoch back (lsa_barrier__funcs.h:39).

5.4 The whole kernel at a glance

Why the block count must not exceed lsaBarrierCountBlock b uses saved-epoch slot 16 + b and inbox slots 48 + 4b … 51 + 4b. With 17 blocks but only 16 barriers, block 16 would read and write its epoch in slot 32 (the multicast inbox), and its inbox slots 112–115 lie past the end of the 112-entry array, in memory that belongs to some other resource. Launching fewer blocks than barriers is fine: the unused barriers stay idle.

6Example 2 · AlltoAll over pure GIN (network only)

06_device_api/02_alltoall_gin/c/main.cu. Every rank sends count floats to every rank (itself included) with one-sided RDMA puts issued from GPU threads. Host requirements: worldGinBarrierCount = 16, ginSignalCount = 16, ginConnectionType = NCCL_GIN_CONNECTION_FULL.

  1. Bind a GIN context. ncclGin loads the backend type, the backend GPU-context handle and the signal-shadow base for context 0 into registers.
  2. Snapshot the signal. Signals are monotonically increasing 64-bit counters that are never implicitly reset. The kernel therefore records the current value and waits for baseline + expected, which keeps it re-launchable.
  3. Entry barrier over the world team, with no fence: pure synchronisation so that no rank writes into a peer's recvbuf before that peer is ready.
  4. One put per destination, issued by the thread whose global id equals the destination rank. The put carries a weak signal increment: when this put's data has landed at rank r, the NIC atomically adds 1 to r's signal signalIndex.
  5. Wait for arrivals. Explained in the next figure. Exactly one CTA per rank receives all nRanks increments.
  6. Flush waits until this context's outgoing puts have been consumed locally, so sendbuf is reusable. It does not mean they are visible remotely; the receiver's signal guarantees that.

8Example 4 · CFT counted AllGather (short tour)

06_device_api/05_allgather_cft_counted/c/main.cu. This needs sm_100+, CUDA 13.3+ and props.cftSupport. The host sets reqs.cftCaps = NCCL_CFT and registers the receive window with NCCL_WIN_COLL_SYMMETRIC | NCCL_WIN_CFT_COUNTED, which reserves a counter area after the payload.

  1. Local slice: copy my own sendbuf into recv[rank], then atomically add my local byte count to my own counter (red.release.sys.add.u64).
  2. Stage through shared memory: TMA memcpy_async_tx moves a chunk into SMEM, because CFT puts read from SMEM (smemSource).
  3. Address a peer: ncclGetCftLeInfo(recvWin, off, peer, team, devComm, &leId, &leOffset) (core__funcs.h:190) turns the window plus peer into a logical endpoint id (ucLeIdBase + flatRank + Δ·stride) and an endpoint offset (mcOffset4K·4096 + off).
  4. Counted put: cft.putCounted(coop, leId, dataOff, counterOff, smem, bytes) writes the data and atomically adds bytes to the destination's counter. Then cft.submit and cft.flush push the batch out.
  5. Completion by byte count: cft.waitCounted(coop, acquire, Generic, counterPtr, bytes·nRanks, abortFlag). No barrier is needed, because the counter reaching the total byte count proves every peer's data has arrived.

Example 06 is the multimem variant: ncclGetMultimemLeInfo and putMultimemCounted issue a single multicast put per chunk that reaches every member of the CFT multimem team. Example 04 shows ncclCftBarrierSession, which is created from reqs.cftBarrierCount.

9Other modules worth knowing

Multimem (NVLS)

With reqs.lsaMultimem = true (or a ncclTeamRequirements entry with multimem), the host binds windows to an NVSwitch multicast object. ncclGetLsaMultimemPointer(win, off, devComm) returns a mcBasePtr + mcOffset4K·4096 + off address. multimem.ld_reduce on it returns the sum across the team in one instruction, and multimem.st broadcasts. See impl/multimem__funcs.h. LSA barriers can also arrive with one multimem.red.

reduce_copy.h

Vectorised, unrolled building blocks: ncclLsaReduceSum, ncclMultimemReduceSum, ncclLsaCopy, ncclLsaReduceSumLsaCopy, and others. They take a Coop plus source/destination lambdas (or ncclSymPtr + team), so you can write an LSA AllReduce in a few lines with peak vector widths (impl/reduce_copy__funcs.h, impl/vector__funcs.h).

LL A2A (ncclLLA2ASession)

A low-latency all-to-all for small messages. Data and a flag are packed into one 16-byte store (the LL protocol), so recv(slot) just spins on the slot. You configure it with reqs.lsaLLA2ABlockCount/SlotCount or ncclLLA2ACreateRequirement, and endEpoch closes a round (ll_a2a.h).

Custom resources

Libraries can add their own symmetric scratch or GIN signals by chaining ncclDevResourceRequirements into reqs.resourceRequirementsList. On return, *outBufferHandle and *outGinSignalStart are filled, and the device gets the memory through ncclGetResourceBuffer*Pointer(devComm, handle, …) (core__funcs.h:250-331).

C / IR entry points

Every templated C++ call has an NCCL_IR_EXTERN_C C-ABI twin (ncclGin_C, ncclGinPut_v3, ncclGinFlush, …) that takes ncclCoopAny. These are used by bindings (bindings/ir/, nccl4py) and by JIT-compiled device code.

ABI compatibility

ncclDevComm.magic/version plus src/devcomm/devcomm_v*.cc let a newer libnccl fill an older struct layout (devCommCopyNewToOld), so pre-compiled kernels keep working across library upgrades. reqs.useRuntimeVersion opts into the current layout for JIT code.

10Memory ordering and pitfalls

MechanismWhat it guaranteesWhat it does not
LSA barrier sync(release) / sync(acquire)Release fence before the inbox store, and acquire on the inbox load. Your plain NVLink stores before sync are visible to peers after their sync.Says nothing about in-flight GIN puts. Use signals or a Put fence for those.
GIN weak signalWhen the receiver sees the increment, that put's payload is visible.Says nothing about earlier puts. Use a strong signal for that.
GIN strong signalThe increment implies this put and all earlier puts on the same context to that peer are visible.Covers other contexts only if you fence them (ncclGinAllContexts).
gin.flush()Local completion: source buffers can be reused.Remote visibility.
GIN barrier, fence PutAfter return, puts from team members to me that were issued before the barrier are visible. Implemented by flushing first when the backend lacks strong signals.—
GIN barrier, fence NonePure rendezvous (cheapest).Any data visibility.
Common mistakes
  • Grid size ≠ barrier count. Each session uses index = blockIdx.x, so launch at most lsaBarrierCount / worldGinBarrierCount / barrierCount CTAs.
  • Wrong requirement for the barrier type: ncclBarrierSession uses barrierCount, while ncclGinBarrierSession(…TagWorld…) uses worldGinBarrierCount. A count of zero leaves the handle pointing at nothing.
  • Waiting for an absolute signal value. Always readSignal a baseline first, or call resetSignal under a barrier, because signals persist across kernel launches.
  • Diverging Coop. Every thread named by the Coop must call (sync() inside is __syncthreads for ncclCoopCta). Calling waitSignal(ncclCoopCta(), …) from a subset of a block deadlocks.
  • Copying sessions is forbidden by design, because the LSA session's destructor persists the epoch.
  • Using LSA pointers for non-LSA peers. ncclGetLsaPointer takes an LSA rank. For world ranks outside the node you must use GIN (or CFT).
  • Non-collective setup. Window registration and ncclDevCommCreate contain bootstrap barriers. All ranks must call them, in the same order.
  • Hang safety. All spin loops poll devComm.abortFlag (set for internal comms) via testAbort. Timeout overloads (sync(…, timeoutCycles), waitSignal(…, timeoutCycles)) return ncclTimeout instead of spinning forever.
