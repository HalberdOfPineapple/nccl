1. How to read the diagrams

Each GPU has the same buffers. The window is the symmetric memory that peers and the switch can reach. localInput and localOutput are private cudaMalloc buffers that no other GPU touches (mm_mix.cu:610-635).

The page uses two kinds of diagram:

  • One-pack diagrams (section 3) follow one 16-byte pack from one thread on GPU 4, step by step. Numbered circles match the numbered list under each diagram.
  • Four-GPU diagrams (sections 4–6) show one arm: which roles run on which GPU, and every stream of packs through the switch. A filled dot marks where a stream starts. A multicast store is one line up from the issuer (dot) that splits into 4 lines down, one to each GPU. An ld_reduce is 4 lines up, one from each GPU, that meet at a + and go down to the issuer as one sum. Each stream is shifted a few pixels, so the number of thin lines at a port is the number of streams through it. Labels such as r0 st on the left name each stream. The numbers on each GPU's link are the measured link data in GB/s (nvidia-smi nvlink -gt d, whole run, from report_summary.json).
multicast store datald_reduce read data and sumsplain load dataplain store dataread request (no data)
How a role gets its address (runRole, mm_mix.cu:313-343). part = rankPartOffset(rank), nextRank = (rank + 1) % 4. 
st_multicast : localInput           -> ncclGetLsaMultimemPointer(window, regionBytes + part, devComm)
ld_reduce    : ncclGetLsaMultimemPointer(window, part, devComm)                -> localOutput
AllReduce    : ncclGetLsaMultimemPointer(window, part, devComm)                -> ncclGetLsaMultimemPointer(window, regionBytes + part, devComm)
plain load   : ncclGetLsaPointer(window, part, nextRank)                       -> localOutput

A Multimem pointer is the multicast address, so the switch sends the access to all 4 GPUs. An Lsa pointer is a plain peer address: one GPU only.

3. Calibration: the five roles, one pack each

The calibration runs one role at a time on all 4 GPUs. It changes only how many CTAs (4 to 64) and how many threads per CTA (256, 512) run the role. The path of a pack does not change, so one diagram per role covers the whole sweep. Each thread does 8 of these packs in a row (8 loads, then 8 stores), with lanes 16 B apart (runChunk, mm_mix.cu:170-183).

multicast store datald_reduce read data and sumsplain load dataplain store dataread request (no data)

3.1 st_multicast

Step function: stepMulticast mm_mix.cu:184-194. Calibration plateau at 32 CTAs × 512 threads/CTA: 93.6 GB/s per GPU, busBW 374.5 (algBW × 1).

  1. The thread loads 16 B from its own localInput with ld.global.v4.f32. Local HBM, no link.
  2. It stores the 16 B with multimem.st.global.v4.f32 to ncclGetLsaMultimemPointer(window, regionBytes + part, devComm). One packet leaves GPU 4.
  3. The switch writes the 16 B into output part 0 on all 4 GPUs. The copy for GPU 4 itself comes back over GPU 4's own link.

3.2 ld_reduce

Step function: stepReduce mm_mix.cu:195-205. Calibration plateau at 32 CTAs × 512 threads/CTA: 89.2 GB/s per GPU, busBW 357.0 (algBW × 1).

  1. The thread issues multimem.ld_reduce.global.add.v4.f32 on ncclGetLsaMultimemPointer(window, part, devComm). Only a request leaves GPU 4.
  2. The switch reads 16 B of input part 0 from all 4 GPUs, also from GPU 4 itself.
  3. The switch adds the four values and returns one 16 B sum to the thread.
  4. The thread stores the sum to its own localOutput with st.global.v4.f32. Local, no link.

3.3 AllReduce on the same CTAs

Step function: stepAllreduce mm_mix.cu:206-216. Calibration plateau at 32 CTAs × 512 threads/CTA: 63.3 GB/s per GPU, busBW 316.5 (algBW × 1.25).

  1. Request: multimem.ld_reduce on the multicast address of input part 0.
  2. The switch reads input part 0 from all 4 GPUs.
  3. The switch returns the sum. The thread must wait for it before it can store.
  4. multimem.st of the sum to the multicast address of output part 0.
  5. The switch writes the sum into output part 0 on all 4 GPUs. Nothing touches localInput or localOutput.

3.4 Plain load on a ring

Step function: stepPlainCopy(peerInput, localDestination) mm_mix.cu:217-227, 337-339. Calibration plateau at 32 CTAs × 512 threads/CTA: 339.6 GB/s per GPU, busBW 339.6.

  1. The thread issues ld.global.v4.f32 on ncclGetLsaPointer(window, part, nextRank): the LSA (peer) address of rank 1's input part 0. A request goes to GPU 5.
  2. GPU 5 returns 16 B through the switch. Only GPU 5 is touched.
  3. The data arrives in the thread's registers.
  4. The thread stores it to its own localOutput. Local, no link.

3.5 Plain store on a ring

Step function: stepPlainCopy(localSource, peerOutput) mm_mix.cu:217-227, 340-342. Calibration plateau at 32 CTAs × 512 threads/CTA: 371.4 GB/s per GPU, busBW 371.4.

  1. The thread loads 16 B from its own localInput. Local, no link.
  2. It stores them with st.global.v4.f32 to ncclGetLsaPointer(window, regionBytes + part, nextRank), the peer address of rank 1's output part 0.
  3. The switch delivers the 16 B to GPU 5 only.
The ring is GPU 4 → 5 → 6 → 7 → 4 (rank r and rank r+1). It is not NCCL's Ring algorithm: there is no step FIFO and no flags. Each GPU just reads from, or writes to, its next neighbour.

4. Multimem table: four arms

All 4 GPUs run the same role table. The question is whether mixing st_multicast and ld_reduce lowers busBW. The separate-CTA arm puts the two roles on different SMs of the same GPU. The same-CTA arm is AllReduce: each thread does the ld_reduce and then the multimem.st.

multicast store datald_reduce read data and sumsplain load dataplain store dataread request (no data)

4.1 NVLS AllGather (st_multicast on all 4 GPUs)

Each GPU sends its own stores once (out about 94) and receives a copy of every GPU's stores, its own included (in 4 × 93.6 ≈ 376).

4.2 NVLS ReduceScatter (ld_reduce on all 4 GPUs)

The reverse: each GPU serves reads of its input part r to all 4 readers (out 4 × 89.2 ≈ 358) and receives only its own sums (in about 90).

4.3 AllGather + ReduceScatter, separate CTAs

Both kinds of stream at once, on different SMs. In = 4m + r = 4 × 60.7 + 67.5 ≈ 310. Out = m + 4r = 60.7 + 4 × 67.5 ≈ 331.

4.4 NVLS AllReduce, same CTAs

The same streams as 4.3. Here each thread's store waits for its own sum, and both rates are equal (63.3). In = out = 5 × 63.3 ≈ 317.

Each GPU loads from rank r+1 and stores to rank r+1, on different SMs. Each link direction carries one load stream and one store stream: for example GPU 4 receives load data from GPU 5 and store data from GPU 7.

6. Split mix: three arms

Ranks 0 and 1 issue st_multicast, and ranks 2 and 3 issue ld_reduce (rank_mask_a=3, rank_mask_b=12). The multicast group always holds all 4 GPUs. So a GPU with no role still receives multicast copies and still serves ld_reduce reads.

multicast store datald_reduce read data and sumsplain load dataplain store dataread request (no data)

6.1 Multicast from ranks 0, 1 (half of an AllGather)

All 4 GPUs receive 2 × 180.1 ≈ 361, from both issuers. GPUs 6 and 7 send nothing.

6.2 Reduce by ranks 2, 3 (half of a ReduceScatter)

All 4 GPUs serve 2 × 152.2 ≈ 305 of reads. Only GPUs 6 and 7 receive sums.

6.3 Split mix: both halves at once

The outgoing link of GPUs 4 and 5 carries both their own multicast stores (64.2) and the read replies for ranks 2 and 3 (2 × 146.6). That is about 358 GB/s, the same as ld_reduce alone. The report suggests that this is why st_multicast falls to 0.356 of its rate alone. This reading is not proven.

7. Link data: how the in/out numbers add up

This section ran nothing new. It reads the link counters of the arms above. The counting rule follows from the one-pack diagrams. For each 16 B pack, all GPUs together:

Role, per 16 B packOut of the issuerInto the issuerOut of each other GPUInto each other GPU
st_multicast16 B (the store)16 B (its own copy back)016 B (a copy)
ld_reduce16 B (its own part, read by the switch)16 B (the sum)16 B (its part, read)0
AllReduce32 B32 B16 B16 B

When all 4 GPUs issue a role at rate x, add up the columns: st_multicast gives in 4x / out x, ld_reduce gives in x / out 4x, AllReduce gives 5x both ways. The plain roles give x both ways. These predictions match the measured numbers in sections 4–6 within about 1–2%. Request packets are not counted, and the counters cannot show the path inside the switch.

8. NCCL cross-check: the same paths in real kernels

nccl-tests runs real collectives on symmetric buffers (-R 2), with one kernel forced by NCCL_SYM_KERNEL. The size is 8 GiB, so each rank's share is 2 GiB, the same as one part in the harness. Differences from the harness, none of which changes the path of a pack:

  • Which bytes rank r handles. In AllReduce, NCCL hands warps round robin over ranks with flattenIx(..., rank, nRanks, block, ...), so rank r's bytes are spread in 4 KiB pieces over the whole buffer, not one 2 GiB part. AllGather and ReduceScatter use rank r's slot rank × nAllElts, like the harness parts.
  • Barriers. Each kernel does an LSA barrier before and after (bar.sync). The harness has one start signal and then loops for 300 ms.
  • Buffers. nccl-tests uses sendbuff/recvbuff and runs out-of-place and in-place. The harness uses the input and output regions of one window and the two cudaMalloc buffers.
