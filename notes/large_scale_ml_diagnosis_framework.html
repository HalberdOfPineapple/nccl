FRAMEWORK

Four functional components. Not necessarily four software modules.

Treat this as an analytical decomposition of a diagnosis system. Components can share signals and algorithms, be integrated into one process, or operate iteratively. Pure profiling tools intentionally occupy only some components.

System versus enabling tool

A diagnosis system ordinarily supplies a detection condition and an attribution method. An observation tool can contribute detailed measurements while leaving detection and RCA to its user. The latter is not a deficient implementation of the former.

Greyhound · detection → validation → actionNeutrino · programmable instruction probing

Problem scope is separate

Specify training or serving; fail-stop, fail-slow, global regression, or incorrect outputs; and target root-cause classes. Likewise, evaluation GT is separate from the detector's runtime reference.

A controlled fault-injection experiment can label known faults even when the deployed detector itself uses peer comparisons or progress invariants.

COMPONENT 01

Observation plane: what becomes visible?

Definition: instrumentation sources and resulting records available to the detector or RCA algorithm, including phase-specific escalations. Direct raw signals must be distinguished from context attached to them and derived/inferred states.

Acquisition

Framework events, NCCL wrappers, CUPTI, eBPF, GPU probes, NIC/device counters, logs and controlled microbenchmarks.

Semantic resolution

Job, step, request, rank, MoE expert, tensor/operator, collective, kernel, instruction, link or component.

Phase and retention

Routine vs triggered, direct vs inferred; continuous export vs event-only capture; record timing/synchronization and overhead.

Semantic layers L0–L3 Software/protocol L4–L5 GPU execution L6–L7 Memory/fabric/health L8–L10

Observation-plane design principle. The important question is not “how many counters?” but which competing causes become distinguishable. More fine-grained information at L7 does not replace missing MoE routing, input-length or dependency semantics at L1–L4.
COMPONENT 02

Degradation detection: compared with what?

Definition: a reference or expectation plus a decision rule that turns observed behavior into an anomaly claim. A measured slowdown is not automatically a fault, and a statistical baseline is not necessarily a truly healthy ground truth.

Same trace, different comparators

Observation Reference / peers

What constitutes an anomaly?

What was measured?→What is expected?→Decision rule

Check whether the comparator assumes equal work, steady execution, stable environment, known protocol progress, or an accurate performance model.

A rank at 45 ms versus peers at 30 ms can be normal if it receives twice as many MoE tokens. Conversely all ranks at 45 ms could be abnormal even though peer comparison sees no outlier.

GT provenance: historical measured run, contemporaneous peers, dynamically learned model, mathematical invariant and simulated ideal are distinct evidence sources.

Central validity check. Ask both: “What exactly is the reference?” and “What makes it a valid comparator for this workload?” A reference can be precise and repeatable without being healthy, comparable or achievable.
COMPONENT 03

Root-cause analysis: how is evidence converted into an explanation?

Definition: a reasoning or experimental procedure that uses available observations to rule out competing hypotheses and identify a responsible mechanism at a stated granularity. Localization (which rank or kernel?) and causal mechanism (why it slowed?) are different outputs.

COMPONENT 04 · OPTIONAL

Mitigation and recovery: closing the loop

Definition: actions taken based on diagnosis, not merely advice about a slow component. Often omitted in observability papers. A mitigation action should ideally have a post-intervention verification step.

Action familyMechanismExamplesRisk / what must be checked
Adapt workload or parallelismMicrobatch changes, pipeline/parallelism adjustment, avoid a slow pathGreyhoundRemediation may change work distribution, memory footprint or synchronization
Qualify/exclude resourcesHealth sweeps; quarantine/re-admit a node after testsGUARD; related operational systemsFalse positives waste capacity; cause may be workload dependent
Restart / replace / restoreHot restart, standby machine, checkpoint rollback and recovery orchestrationByteRobust · Aegis-related operational handlingRecovery cost, lost work, service continuity
Policy-defined controlHooks for custom GPU/fabric policiesgpu_ext · fabric_extProgrammability alone does not define a safe or effective recovery policy

Measure the outcome, not the mere action. A successful quarantine or reconfiguration should restore a workload-conditioned performance target without introducing correctness problems or excessive adaptation overhead.

Online/offline belongs to each stage

Example: NIXT can collect NCCL Inspector records while a job runs, yet perform comparative RCA later. GUARD combines online screening with offline node sweeps. Neither is well described by a single “online: yes/no” field.

Automation belongs to each decision

A system can automatically collect → detect → localize and still require a human to decide the root cause. “High automation” without stages is ambiguous.

SYNTHESIS / RESEARCH DESIGN

From a literature map to a research question

1 · What can be observed?

Can we causally associate a logical ML operation with host execution, GPU instructions, communication progress and resource telemetry?

2 · What counts as a degradation?

Can comparisons account for variable sequence length, MoE routing, communication volume and concurrent traffic rather than relying on a fixed latency baseline?

3 · What can be distinguished?

Can the system rule out late producers, synchronization waits, GPU memory behavior and fabric contention, rather than merely reporting “slow NCCL”?

A useful experimental specification

True scale-up fabric degradationTopology, concurrent traffic, expected transfer characteristicsFabric/link health, transfer progress, controlled isolated testsIncreasing load or changing communication algorithm can mimic degradation
Global compiler/runtime regressionComparable operator semantics and build/configurationCPU stacks, kernel timing, compiler/kernel metadataAll workers slow together; peer outliers disappear
Unifying question: What minimum, causally linked, workload-aware observation set allows important performance-degradation hypotheses to be distinguished in real ML workloads—and which detection/reference and RCA procedure can exploit it efficiently?
