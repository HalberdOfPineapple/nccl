Two NVLS AllReduce paths: from all_reduce_perf to multimem

NCCL has two ways to run an AllReduce with NVSwitch multicast on one node. Both end in the same two PTX instructions. This page follows one ncclAllReduce call through each path: from nccl-tests, through NCCL's host code, into the GPU kernel, down to the instruction. It explains the arms "NVLS" and "Symmetric multicast" of the AllReduce scalability series.

Linked badges such as enqueue.cc:1992 open the file at the v2.32.3-1 tag on GitHub; the line is the same in this checkout. One file, src/device/all_reduce.h, has local comment edits: its badges show the local line and link to the tag line. Grey badges such as common.cu:563 are nccl-tests (/root/nccl-tests/src, commit afd59ab), and host_table.cc:2844 marks generated files under build/obj/device/gensrc. Chain tags: host runs on the CPU, device runs in the GPU kernel, ptx is the instruction itself.

The case traced: all_reduce_perf -t 1 -g 8 -b 2G -e 2G -d float -o sum on 8 H100 GPUs of one node. One process drives all 8 GPUs. For NVLS the run uses -R 0 and NCCL_ALGO=NVLS NCCL_PROTO=Simple. For symmetric multicast it uses -R 2 and NCCL_SYM_KERNEL=allreduce:AllReduce_RSxLDMC_AGxSTMC. Other environment variables keep their defaults.

1The short answer

Both paths reach the NVSwitch through two PTX instructions:

  • multimem.ld_reduce.relaxed.sys.global.add.v4.f32 reduce_kernel.h:1172: one load through a multicast address returns the sum of the 16 bytes at that address on every GPU.
  • multimem.st.global.v4.f32 op128.h:437: one store through a multicast address writes the same 16 bytes on every GPU.

A multicast address is a virtual address that the driver maps to "the same buffer on every GPU of the group". NCCL creates it with cuMulticastCreate and binds real memory to it with cuMulticastBindMem or cuMulticastBindAddr. The two paths differ in which memory is behind that address and who issues the instructions:

NVLS
  • The switch works on NCCL's own buffer, set up by NCCL. Your buffer is never seen by the switch.
  • Each CTA runs a 3-stage pipeline: copy your data into NCCL's buffer, reduce through the switch, copy the result out.
  • Stages and GPUs synchronise through step flags, every 128 KiB chunk.
Symmetric multicast
  • The switch works on your buffer, after you register it as a symmetric window (-R 2).
  • Every thread does load-reduce then store, on its share of the data.
  • One barrier across GPUs at the start of the call and one at the end.

1.1 What one multimem instruction does

A multimem instruction is issued by one thread, like an ordinary load or store. The difference is the address: it is a multicast address, so the request goes to the NVSwitch instead of to one GPU's memory.

Instruction (as NCCL uses it for float sum)Bytes per threadWhat the thread gets or causesCode
multimem.ld_reduce.relaxed.sys.global.add.v4.f32 {r0,r1,r2,r3}, [mcAddr]16 (4 floats)4 registers holding, for each of the 4 floats, the sum of that float over all GPUs bound to the multicast address. The issuing GPU's own copy is included.reduce_kernel.h:1172
multimem.st.global.v4.f32 [mcAddr], {r0,r1,r2,r3}16The same 16 bytes are written into every GPU's copy at that address. The thread does not wait for the writes to finish.op128.h:437
multimem.ld_reduce….add.f32 / multimem.st.global.b324Same, one float. NCCL uses these only for the few elements at the start or end that do not fill a 16-byte pack.reduce_kernel.h:1131, op128.h:429
multimem.ld_reduce.acquire.sys.global.min.u648NVLS only: the smallest value of a 64-bit step counter over all GPUs (§6.3).prims_simple.h:90
multimem.red.release.sys.add.u32 [mcAddr], 14Symmetric kernel only: adds 1 to a barrier counter on every GPU; returns nothing (§7.3).lsa_barrier__funcs.h:62

16 bytes is the largest pack NCCL uses for these instructions. LoadMultimem_BigPackSize picks 16 bytes for floating-point sum with elements smaller than 8 bytes, and the element size otherwise (reduce_kernel.h:1258-1269). So with float, one instruction moves 16 bytes of payload for one thread. To move 2 GiB, the GPUs together issue 2 GiB ÷ 16 B = 134 million load-reduce instructions and the same number of stores. Each GPU issues 1/8 of them.

1.2 How threads share the work

The instruction does not coordinate threads; each thread works alone. Threads cooperate only through which addresses they are given. Both kernels use the same layout:

  1. Lanes of a warp take neighbouring 16-byte packs. Lane l starts at byte 16 × l of the warp's piece (common_kernel.h:54-55; all_reduce.cuh:455-456). The 32 lanes together cover 512 contiguous bytes, so the hardware can combine the requests the same way it coalesces ordinary loads. How these requests are packed on NVLink is not documented by NVIDIA and was not measured here.
  2. Each thread issues 8 loads before it stores. The unroll factor is 8 on H100 (ncclCollUnroll, device.h:576-578; the symmetric kernel uses UnrollPacks = 16·8/16 = 8, all_reduce.cuh:449). The 8 load-reduces go to addresses 512 B apart and do not depend on each other, so all 8 can wait at the switch at the same time. A warp therefore covers 8 × 512 B = 4 KiB per round (common_kernel.h:48). Then the thread issues its 8 stores.
  3. Warps take neighbouring 4 KiB pieces and then jump ahead by (number of warps × 4 KiB), so no two threads ever touch the same bytes.
  4. GPUs take different pieces. In NVLS, GPU h reduces only the slice of each chunk that belongs to head h. In the symmetric kernel, the thread number counts over all GPUs (rank is part of flattenIx), so the 4 KiB pieces are dealt out to the GPUs in turn. Either way each byte is load-reduced by exactly one thread on exactly one GPU, and stored by that same thread to all GPUs.

4Setup before the first call

A multimem instruction needs a multicast address, and memory must be bound behind it. The two arms prepare this at different times and with different memory.

4.1 NVLS: NCCL builds its own multicast buffer

At communicator init, NCCL creates one multicast group per communicator and reserves address space for three things: progress flags ("credit"), data slots, and user-buffer registration. Only the flags are backed by memory at init. Because NCCL_RUNTIME_CONNECT=1 by default (init.cc:65), the data slots get memory on the first NVLS collective, in ncclNvlsBufferSetup.

4.3 Both kernels use symmetric memory, in different senses

A multimem instruction only works on memory that is bound to a multicast object at the same offset on every GPU. So both kernels need symmetric memory. The confusion comes from the word "symmetric", which is used in two senses:

SenseWhat it isNVLSSymmetric kernels
Hardware sense: memory multimem can work ona multicast object, with memory of every GPU bound to it at the same offsetyes, on NCCL's own bufferyes, on the user's buffer
NCCL API sense: the "symmetric memory" feature (since 2.27)the user registers their buffers with ncclCommWindowRegister(…, NCCL_WIN_COLL_SYMMETRIC)noyes

When NVIDIA's documents say "symmetric memory", they mean the second sense. NVLS does not use that feature, but it builds a symmetric buffer of its own, because multimem cannot work without one.

What multimem requires: the same offset, not the same address

Each GPU maps the multicast object at its own virtual address: every rank reserves its own range (multicast.cc:149-150 for NVLS, dev_runtime.cc:515-519 for windows), and the addresses may differ between GPUs. What must match is the offset inside the multicast object. A multimem instruction on any GPU is translated to (multicast object, offset), and the NVSwitch reads or writes that offset on every member GPU.

In one sentence: both kernels need memory bound at the same offset on every GPU; NVLS provides it with its own buffer and copies data through it, and the symmetric kernels get it by having the user register their buffer, so no copies are needed.

9Why the two designs differ

Both kernels issue the same two multimem instructions. They differ in everything around those instructions, because they were built for different jobs. In short: NVLS pays at run time so the user pays nothing; the symmetric kernel makes the user pay once at setup so the run-time path is as short as possible.

NVLS: accept any buffer, on one node or many
  • Any user buffer, no setup. The switch only works on memory bound to a multicast object, and binding is a collective, page-aligned step. So NCCL binds its own 256 MiB buffer once and copies user data through it (scatter and gather teams).
  • A fixed buffer is reused (8 steps × 128 KiB per slot), so every step needs flow control: "filled" and "free" flags, checked across all GPUs with multimem.ld_reduce.min.
  • Same code for many nodes. It lives in NCCL's classic channel and Primitives framework, like Ring, and has a network branch where the sum goes to a network peer (all_reduce.h:458-521). A step-by-step pipeline with flags is how NCCL feeds networks.
Symmetric multicast: fastest path inside one node
  • The user registers once. Buffers come from ncclMemAlloc and are registered as windows, collectively. NCCL binds the user's buffer to the multicast range at that time (§4.2).
  • No staging buffer, so no slots to reuse and no flow control. The kernel only needs inputs to be ready before anyone reads, and every store to be done before anyone leaves: one barrier at each end.
  • The price is on the user's side: a collective registration step, allocation rules, one NVLink domain only, and no multicast with 2 GPUs (sym_kernels.cc:194-196).

9.1 How the two paths arrived

The two paths come from different NCCL releases. The years follow the timeline note in the repo (notes/nccl_nvls_development_timeline.md); the version numbers were checked against NCCL's own documentation where stated.

Three paths, not two. Between the two kernels this page compares sits registered classic NVLS (§6.2): the classic pipeline without the copies. A comparison of "classic NVLS against symmetric kernel" therefore mixes two effects, the copies and the kernel design. Only the three-way test in §10.6 separates them.

10.1 How many CTAs each kernel needs

Chart 9. algBW against CTAs requested, 8 GPUs, 2 GiB per GPU, median of 3 runs. Threads per CTA: NVLS 640, symmetric multicast 512. Hover a point for values. NCCL's own choice is 16 CTAs for NVLS and 2 for symmetric multicast.

Table view
  • Per CTA, the symmetric kernel moves about 6× more (measured): 276.1 GB/s ÷ 2 CTAs = 138 GB/s per CTA, against about 22 GB/s per CTA for NVLS up to 4 CTAs (44.2 at 2, 87.7 at 4).
  • Most of that gap is the number of warps issuing multimem (from the code): 4 of 20 warps in an NVLS CTA (§6.2) against 16 of 16 in a symmetric CTA, a factor of 4.
  • The rest is plausibly the per-step stops (reasoning): every NVLS slice has two flag waits and two team barriers (§8.1), during which the data warps issue nothing. This split was not measured; per-warp stall reasons from ncu would show it.
  • NVLS reaches full speed only by using many CTAs. With 16 CTAs it has 64 issuing warps per GPU; the symmetric kernel needs 32.

10.2 Small payloads

Chart 10. algBW against payload per GPU, 8 GPUs, CTAs chosen by NCCL (NVLS 16 × 640, symmetric multicast 2 × 512, the same at every payload), median of 5 runs. Hover a point for values.

Table view
  • At 8 GPUs, classic NVLS leads Ring only from 128 MiB; symmetric multicast leads at every payload (measured): NVLS ÷ Ring is 1.01 at 32 MiB (165.5 against 163.6 GB/s), 1.20 at 128 MiB and 1.31 at 8 GiB; symmetric multicast ÷ Ring is 1.52 at 32 MiB (248.1 GB/s) and 1.31 at 8 GiB. Across GPU counts, the GPU count decides first: both multimem arms gain on Ring as N grows, and at 2 GPUs NVLS loses at every payload (see the payload report, corrected 2026-11-18).
  • Why (reasoning): NVLS has fixed costs per call. The 3-team pipeline must fill before the reduce team starts and drain after it ends, and every step waits on flags from all 8 GPUs. At 32 MiB per GPU, each of the 16 channels handles only 2 MiB, so a few pipeline rounds must carry those costs. The symmetric kernel's fixed cost per call is two barriers.
  • Why it matters for LLM work: gradient buckets of about 25 MiB (PyTorch DDP default) fall in exactly the range where NVLS loses most.
  • Test that would confirm it: sweep NCCL_NVLS_CHUNKSIZE at 32–256 MiB. If fill, drain and per-step waits are the cost, the step size should move the small-payload rate.

10.4 A cost NVLS hides: traffic in each GPU's own memory

  • Alone, this cost is hidden: half of the memory bandwidth is still free, and NVLS reaches the same ceiling as the symmetric kernel.
  • Next to other work it may not be hidden (reasoning, not tested): when a co-running kernel uses memory bandwidth, as in the memory co-runner experiments of this project, NVLS competes for about three times as many bytes as the symmetric kernel.

10.5 Stability across GPUs, and the 2-GPU case

  • NVLS is stable (measured): busBW 302–310 GB/s from 2 to 8 GPUs; changing the GPU set at 2, 4 or 6 GPUs moves it by at most 0.8%.
  • The symmetric kernels are not (measured): at 6 GPUs, symmetric multicast varies by 6.7% between four GPU sets and plain load/store by 14%; in the payload sweep, where buffers are sized for 8 GiB, they differ by up to 3% from fixed-size runs. Splitting 2 GiB evenly over 6 GPUs changes nothing.
  • A plausible design link (not tested): NVLS always works on its own buffer with a fixed 128 KiB-per-slot layout. The symmetric kernel works on the user's buffer and hands 4 KiB pieces to GPUs in turn, piece k to GPU k mod N (§7.2), so which addresses each GPU touches depends on the rank count and on where the buffer lies.
  • At 2 GPUs, NVLS is slower than Ring (206.5 against 339.5 GB/s, measured). This is the algorithm, not the warps: with 2 GPUs, multimem AllReduce moves 1.5 link bytes per payload byte and Ring 1.0, as the link counters confirmed. Symmetric multicast does not exist at 2 GPUs.
