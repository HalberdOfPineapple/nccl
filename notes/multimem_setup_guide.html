1. Short answer: which addresses, which handles

Earlier I said each GPU has "a normal address and a multicast address" for its buffer. In the code there are actually three kinds of address for one window on one rank, plus two kinds of handle:

KindName in codeWhat the GPU's page table maps it toWhere it is created
Address 1: the user's own pointerstate.windowMemory (in NCCL: userPtr, mem->primaryAddr)This GPU's own physical pagesncclMemAlloc: cuMemCreate + cuMemAddressReserve + cuMemMap allocator.cc:62-89
Address 2: the LSA (unicast) slots, one per rankdevr->lsaFlatBase + r*bigSize + bigOffset, for r = 0..3Slot r maps rank r's physical pages over NVLink. The slot for my own rank maps my own pages again (a second alias of address 1)symMemoryMapLsaTeam dev_runtime.cc:397, 345, 331

Handle B: the multicast objectCUmemGenericAllocationHandle mcHandle (stored as t->mcHandle)(not an address) names the multicast objectcuMulticastCreate on team rank 0, imported by the others multicast.cc:27, 54-60

So, concretely:

  • mcHandle is an integer handle, valid only inside this process, that names one driver object: the multicast object. It works like a file descriptor. Each rank holds its own number, but all four numbers refer to the same object.
  • The multicast object is what cuMulticastCreate creates. It has a size (bigSize), a fixed list of member GPUs (filled by cuMulticastAddDevice) and, for each offset range, the physical pages each member bound there (filled by cuMulticastBindAddr). The NVSwitch uses that list to deliver or gather data.
  • mcBasePtr is an ordinary virtual address in this GPU's address space, the start of a bigSize-long range that cuMemMap pointed at the multicast object instead of at memory. It is per rank: each rank reserves its own range, so the number can differ between GPUs.
  • The multimem pointer that a kernel uses is mcBasePtr + bigOffset + offset.

What all ranks agree on. Only two things are truly shared: the multicast object, and each rank's physical pages (which peers import). Everything else that must match (bigSize, bigOffset, so stride4G and mcOffset4K) matches because every rank computes it the same way. That is why window registration is a collective call that every rank must make with the same sequence of windows.

3. Address map of one GPU (rank 2)

The numbers are illustrative but follow the code's formulas: bigSize = 80 GiB = 0x14_0000_0000, and our window sits at bigOffset = 0x4000_0000 (1 GiB). NCCL's own internal window, created first, occupies the space below it. The virtual base addresses (0x7d80…, 0x7e00…, 0x7f2a…) are made up; the driver chooses them.

GPU 0 has the same picture with different base numbers, for example mcBasePtr = 0x7c40_0000_0000. Its multicast address for our window is then 0x7c40_4000_0000: a different number, but the same offset 0x4000_0000 into the same object, so it reaches the same four sets of pages.

4. Setup, step by step, in mm_mix.cu

The harness's setupRank (mm_mix.cu:590-618) makes four calls on each rank:

ncclCommInitRank(&state.communicator, rankCount, shared.identifier, rank);           // step 1
ncclMemAlloc(&state.windowMemory, windowBytes);                                       // step 2, 16 GiB + control
ncclCommWindowRegister(state.communicator, state.windowMemory, windowBytes,
                       &state.window, NCCL_WIN_COLL_SYMMETRIC);                       // step 3
requirements.lsaMultimem = true;
ncclDevCommCreate(state.communicator, &requirements, &state.deviceCommunicator);     // step 4

Each step below lists what is created and what crosses between ranks. "Bootstrap" is NCCL's host-side messaging between processes (sockets), used only during setup.

Step 1: ncclCommInitRank

  • Ranks find each other and all-gather peerInfo, which includes each GPU's totalGlobalMem. That is the input for bigSize later.
  • No symmetric or multicast state exists yet.

Step 2: ncclMemAlloc(&windowMemory, size) allocator.cc:17-89

  • cuMemCreate(&handle, size, ...): allocates physical pages P2 on this GPU and returns handle A.
  • cuMemAddressReserve + cuMemMap + cuMemSetAccess: picks a virtual range and maps it to P2. That range is windowMemory (address 1).
  • Purely local. Nothing is shared. The reason to use ncclMemAlloc instead of cudaMalloc is that this memory has a handle that can be exported and bound to a multicast object.

Step 3: ncclCommWindowRegister dev_runtime.cc:1800 → ncclDevrWindowRegisterInGroup 1149

3a. First symmetric window: NCCL builds its own internal setup (ncclSymkInitOnce, dev_runtime.cc:1177 → sym_kernels.cc:185)

  • ncclDevrInitOnce computes lsaSize, lsaSelf and bigSize = max totalGlobalMem, rounded up to 4 GiB dev_runtime.cc:160-200. Every rank gets the same bigSize without sending anything.
  • NCCL then creates an internal device communicator for its own symmetric kernels with lsaMultimem = true (when NVLS is available and the team has more than 2 ranks) sym_kernels.cc:194-196, 254. That call reaches symTeamObtain(comm, lsa, multimem=true, ...), and this is where the multicast object is created:
// dev_runtime.cc:495-528  (inside symTeamObtain)
mcProp.numDevices = team.nRanks;          // 4
mcProp.size       = devr->bigSize;        // 80 GiB
if (team.rank == 0) {
  ncclMcCreate(comm, &mcProp, ..., &mcHandle, shareableHandle);   // cuMulticastCreate   (multicast.cc:27)
  bootstrapIntraNodeBroadcast(..., shareableHandle, ...);          // send a reference to the others
} else {
  bootstrapIntraNodeBroadcast(..., shareableHandle, ...);          // receive it
  ncclMcImport(comm, shareableHandle, rank0, &mcHandle);           // get my own handle to the same object
}
cuMulticastAddDevice(mcHandle, comm->cudaDev);                     // join: this GPU becomes a member
cuMemAddressReserve(&mcAddr, devr->bigSize, ...);                  // pick a virtual range on this GPU
cuMemMap(mcAddr, devr->bigSize, 0, mcHandle, 0);                   // point that range at the object
t->mcHandle  = mcHandle;
t->mcBasePtr = (void*)mcAddr;                                      // address 3's base
  • On this machine the handle type is CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR (cudawrap.cc:19). Rank 0 broadcasts its handle value, and each other rank asks rank 0's proxy thread for a file descriptor (ncclProxyClientGetFdBlocking) and turns it into its own handle with cuMemImportFromShareableHandle multicast.cc:54-56.
  • The internal setup also registers a small NCCL resource window (barriers and similar). It takes the first piece of the bigSize space, which is why our window does not start at offset 0.

3b. Our window: agree on an offset and share the pages (symMemoryObtain, dev_runtime.cc:1207 → 698)

cuMemRetainAllocationHandle(&memHandles[0], windowMemory);       // get handle A back from the pointer (1200)
bootstrapAllGather(globalSegmentInfo);                            // every rank learns every rank's size and flags (753)
mem->lsaMaxSize = max(size over ranks);  mem->lsaMinSize = min(...);  // (808-809)
ncclSpaceAlloc(&devr->bigSpace, bigSize, lsaMaxSize, granularity, &bigOffset);   // (814) same answer on every rank
mem->bigOffset = bigOffset;

Then symMemoryMapLsaTeam builds the unicast slots (address 2):

symMemoryExportSegmentHandle(...);                  // turn handle A into something shareable
bootstrapIntraNodeAllGather(messages);               // every rank receives every rank's page handle   (389)
cuMemAddressReserve(&lsaFlatBase, lsaSize*bigSize);  // first time only                                (397)
for r in 0..3:
  addr = lsaFlatBase + r*bigSize + bigOffset;        //                                                (345)
  import rank r's handle;  cuMemMap(addr, size, 0, handle_r, 0);   // slot r → P_r                     (331)
bootstrapIntraNodeBarrier(...);

Then every existing team with a multicast object binds this window into it (dev_runtime.cc:853-855 → symBindTeamMemory 422):

cuMulticastBindAddr(tm->mcHandle,          // the shared object
                    mem->bigOffset,        // where in the object (same on all ranks)
                    mem->primaryAddr,      // = windowMemory: MY pages
                    mem->lsaMinSize, 0);   // how much (smallest window size among ranks)

Each rank binds only its own pages. After all four have run this line, the object holds "offset bigOffset → P0, P1, P2, P3".

3c. Build the device record (symWindowCreate, dev_runtime.cc:1214 → 1000)

winDevHost->lsaFlatBase = devr->lsaFlatBase + win->bigOffset;   // 0x7e00_4000_0000 on rank 2
winDevHost->mcOffset4K  = win->bigOffset >> 12;                  // 0x40000
winDevHost->stride4G    = devr->bigSize  >> 32;                  // 0x14 (= 20, i.e. 80 GiB)
winDevHost->lsaRank     = devr->lsaSelf;                         // 2
cudaMemcpyAsync(winDev, winDevHost, sizeof(ncclWindow_vidmem), H2D);
*outWinDev = winDev;                                              // this is state.window (ncclWindow_t)

Finally bootstrapBarrier (1222): no rank returns until all have finished binding.

Step 4: ncclDevCommCreate(..., lsaMultimem = true) dev_runtime.cc:1977 → ncclDevrCommCreateInternal 1399

  • symTeamObtain(comm, lsa, lsaMultimem=true, ...) 1513 finds the LSA team from step 3a, which already has mcBasePtr != nullptr (473), so it creates nothing new.
  • outDevComm->lsaMultimem.mcBasePtr = tmLsa->mcBasePtr; 1516: copies this rank's base address into the struct the kernel will receive.
  • It also registers its own small resource window (barriers), the same way as step 3b.

If no symmetric window had been registered before this call, the multicast object would be created here instead. Any window registered later would then be bound at 855; any window registered earlier is bound at 532. Either order ends in the same state.

6. Run time: one multimem.st from the kernel to four GPUs

In the multicast role, rank 2 writes its 2 GiB part of the output region of the window (mm_mix.cu:314-325):

const size_t part = rankPartOffset(arguments.rank);                 // 2 * 2 GiB = 0x1_0000_0000
const uintptr_t output = (uintptr_t)ncclGetLsaMultimemPointer(
    arguments.window, regionBytes + part, arguments.deviceCommunicator);   // offset 0x3_0000_0000 into the window
...
storeMulticastPack(output + offset, value);                          // per 16 bytes

Pointer arithmetic (core__funcs.h:176-186), with rank 2's illustrative values:

ncclGetLsaMultimemPointer(w, off, comm) = ncclGetMultimemPointer(w, off, comm.lsaMultimem)
  ptr  = mm.mcBasePtr                       // 0x7d80_0000_0000   (devComm, per rank)
  ptr += w->mcOffset4K * 4096               // + 0x4000_0000      (window record: bigOffset)
  ptr += off                                // + 0x3_0000_0000    (offset inside the window)
                                            // = 0x7d83_4000_0000

The instruction (mm_mix.cu:148-152):

multimem.st.global.v4.f32 [0x7d83_4000_0000], {x, y, z, w};

What happens to it:

  1. GPU 2 translates 0x7d83_4000_0000 through its page table. Because cuMemMap(mcAddr, …, mcHandle) mapped that range to the multicast object, the translation gives "multicast object, offset 0x3_4000_0000", not a physical page.
  2. The 16 bytes go out once on GPU 2's NVLink, to the NVSwitch.
  3. The switch looks up that offset in the object. The offset falls in our window (0x4000_0000 … +16 GiB), which all four ranks bound, so it finds P0, P1, P2 and P3.
  4. It writes the 16 bytes into each of them at window offset 0x3_0000_0000, which is each rank's windowMemory + 0x3_0000_0000. GPU 2's own copy also comes back in over GPU 2's link.
  5. Nobody is notified. A rank that wants to read the result must first synchronize, for example with a barrier through the device communicator.

For comparison, the plain-store role (mm_mix.cu:338-341) uses an LSA slot instead:

ncclGetLsaPointer(w, off, peer=3) = w->lsaFlatBase + 3 * (stride4G << 32) + off
                                  = 0x7e00_4000_0000 + 3*0x14_0000_0000 + off   // slot 3 → P3 only

That address translates directly to P3, so the switch routes the store to GPU 3 alone.

7. Run time: one multimem.ld_reduce

input = ncclGetLsaMultimemPointer(arguments.window, part, arguments.deviceCommunicator);  // mm_mix.cu:330
multimem.ld_reduce.global.add.v4.f32 {a, b, c, d}, [input + offset];                      // mm_mix.cu:142
  1. Same translation: the address means "multicast object, offset X".
  2. GPU 2 sends one read request to the switch.
  3. The switch reads the 16 bytes at offset X from P0, P1, P2 and P3, so each GPU's outgoing link carries one copy.
  4. The switch adds the four float4 values and returns one reply, the sum, to GPU 2.

8. Things that are easy to mix up

ConfusionWhat the code actually does
Two fields named lsaFlatBasedevr->lsaFlatBase (host) is the start of the whole 4-slot range. ncclWindow_vidmem::lsaFlatBase (device) is already shifted by this window's bigOffset dev_runtime.cc:1026. The window record has no separate bigOffset for unicast; it is baked into this field.
mcHandle vs mcBasePtrmcHandle names the object and is only used by host driver calls (AddDevice, cuMemMap, BindAddr). mcBasePtr is a GPU virtual address and the only thing a kernel sees.
Is the multicast object "memory"?No. It holds no data. Data lives only in P0..P3. The object is a size, a member list and a table of bound pages.
windowMemory vs ncclGetLocalPointerBoth reach my pages P2. ncclGetLocalPointer returns my LSA slot (lsaFlatBase + lsaRank·stride), which is a second mapping of the same pages, not the windowMemory number.
How do ranks agree on bigOffset?They don't send it. All ranks run the same allocator on the same inputs in the same order. If ranks registered different windows or in a different order, the offsets would disagree and the setup would be wrong, so registration must be collective.
Is the whole bigSize range usable?No. Only offset ranges that every member has bound, which means only registered windows, and only up to lsaMinSize of each.
Can a multimem op target only some GPUs?No. It always reaches every member of the object. A subset needs a separate team with its own multicast object.

9. How to see the real values on our machine

The numbers in sections 3 and 6 are illustrative. NCCL prints the real ones when run with:

NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,NVLS,ALLOC

The lines to look for:

  • Symmetric VA size=80GB: bigSize dev_runtime.cc:201
  • NVLS Creating Multicast group nranks 4 size …: the object being created on team rank 0 multicast.cc:26
  • Binding multicast memory at big=… size=… to team {4 x 1}: each window's bigOffset and bound size dev_runtime.cc:430

Printing mcBasePtr and ncclGetLsaMultimemPointer from a kernel would also show that the base differs between ranks while the offset is the same. None of this has been run yet, because it needs the GPUs.
