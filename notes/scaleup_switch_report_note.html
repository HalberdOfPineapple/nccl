Reading note: Shouxu’s scale-up switch report

A structured restatement of the report (4 pages). Each experiment has its motivation, configuration, data path, results and interpretation. The author’s claims and our reading notes are kept apart: purple boxes are ours, not the author’s.

The report is a chain of eliminations. Sections 1 and 2 set the reference (about 700 GB/s per operation). Section 3 tests four explanations for the lower AllReduce, and keeps the last one.

1. Multimem operations alone, without NCCL

Motivation

Set the reference: how fast each multimem operation can go on its own, before NCCL’s own overheads.

Configuration

GPUs, blocks, threads, sizeNot stated in this section

Data path

Results

OperationbusBW, GB/s
st_multicast aloneabout 700
ld_reduce aloneabout 700

Interpretation

Author: each operation can saturate NVLink bandwidth.

Our note. “Saturate” is not shown with a link counter. 700 GB/s is 91% of the 768 GB/s the report later measures for one plain load. busBW for AllGather and ReduceScatter at 4 GPUs is 3 × the per-GPU rate, while on our H100 the busiest link direction carries 4 × that rate. If GB300 behaves the same, 700 GB/s busBW would need about 933 GB/s per direction, more than any plain transfer in the report. So either GB300 does not send the issuing GPU’s own copy over its link, or its link limit is above 768 GB/s.

Interpretation

Author: without registration, 8 of 20 blocks only copy data, so fewer blocks issue multimem. Registering the buffers removes this overhead.

Our note. The report gives the mechanism (fewer issuing blocks) but no test of it, such as giving the default path more blocks. The block count after registration is not stated. On our H100, NCCL 2.32.3 chose 4 blocks × 512 threads for registered collectives at this size.

3. The AllReduce gap

Motivation

AllReduce does both operations: ld_reduce, then st_multicast. With registered buffers, it should avoid the section 2 overhead. It does not reach the 700 GB/s of the single operations.

Configuration

KnobValue
CollectiveNCCL AllReduce, registered buffers
Other settingsNot stated; presumably as in section 2

Data path

Results

CollectivebusBW, GB/s
AllReduce, registeredabout 550

Interpretation

Author: there must be some other overhead. Sections 3.1–3.4 test four candidates.

Our note. busBW does not compare directly between collectives. AllReduce busBW at 4 GPUs is 6 × the per-GPU rate; AllGather and ReduceScatter are 3 ×. On our H100, AllReduce carries 5 × its rate in each link direction, so its best busBW is 1.2 × the link limit per direction. With GB300’s plain-load 768 GB/s as that limit, the best would be about 920 GB/s (or about 1150 if the own copy does not use the link). 550 GB/s is 48–60% of that, so the gap is larger than “550 versus 700” suggests.

3.1 Hypothesis 1: more transfers through the switch

Motivation

A cited NSDI paper reports that performance sometimes falls when more transfers cross NVSwitch. AllGather and ReduceScatter use the links unevenly, while AllReduce keeps every link busy, so AllReduce has more active transfers.

Interpretation

Author: busBW does not drop for plain or multimem operations, so this is not the cause.

Our note.

  • The two plain pairs use different links, so adding the second pair does not load any shared link direction. The test shows the switch can carry two independent pairs; it does not test more transfers on the same link.
  • The arrow means “who accesses whom”, not data direction: for “G0 ← G1” load, G0 loads from G1, so data flows G1 to G0. Section 3.2 writes the same run as “g0 → g1”.
  • Plain store is 10% below plain load (691 versus 768). The report does not discuss it.
  • For the 2-GPU multimem rows, it is not stated whether the multicast group had 2 or 4 GPUs. The two cases load G2 and G3 differently.

Interpretation

Author: two-way traffic costs something, more for loads, maybe because load requests going one way interfere with data going the other way (a SIGCOMM paper shows this for PCIe). But each direction still reaches about 660 GB/s. So AllReduce should only fall from 700 to about 670, not to 550. Not the main cause.

Our note. The argument compares AllReduce busBW with a per-direction link rate, but AllReduce busBW is not a link rate (see section 3). Using 662 GB/s as the two-way limit, AllReduce could still reach about 790 GB/s busBW (1.2 × 662) or more. So the conclusion holds, even more strongly than the author argues.

3.3 Hypothesis 3: multicast and reduce interfere in the switch

Motivation

In AllReduce, the switch handles multicast and reduce traffic at the same time. Something in the switch might slow one or both.

Results

GroupbusBW, GB/s
G0, G1 AllGather, during the split runabout 690
G2, G3 ReduceScatter, during the split runabout 690

Interpretation

Author: each group keeps about 690 GB/s, so interference in the switch is not the cause.

Our note. This only clears the switch for this traffic, where no link direction carries both operations. On our H100 we ran the same split with one multicast group of all 4 GPUs. Then G0 and G1 also serve the reads of G2 and G3, and st_multicast fell to 36% of its rate alone, while ld_reduce kept 96%. So the group layout decides the result, and the report should state it.

Interpretation

Author: when one GPU issues both operations, busBW falls from about 700 to 550–560 GB/s, whether one block does both or separate blocks do. Plain loads and stores do not fall. A possible cause is a shared limit on in-flight multimem requests: one operation alone can keep enough requests in flight to fill NVLink, but two operations share the limit and neither fills it.

Errors in the tables. The plain ld/st table says “32 blocks issue st_multicast” for loads and “ld_reduce” for stores. This looks copied from the multimem table. The plain values (662.3, 668.1) are exactly the ring values of section 3.2, so these rows were probably reused from that run.

Our note.

  • The “+” rows need a formula. If 560 is the sum of the two operations, the links are well below full (about half to 60%, depending on whether the issuing GPU’s own copy uses its link). If each operation reaches 560, the links are close to full and no extra limit is needed. The report does not say.
  • The in-flight limit is a hypothesis; no experiment tests it. Tests that could: vary the blocks of one operation while the other stays at 32 blocks, and read link counters.
  • We repeated this section on 4 H100 GPUs. busBW did not fall: AllReduce was 1.38 × the single operations, in our code and in NCCL. But each operation’s rate did fall when mixed (−35% and −24%), and the busiest link direction carried 9–13% less, against 3% for plain traffic. See the H100 report.
